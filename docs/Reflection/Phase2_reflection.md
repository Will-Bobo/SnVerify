【A. 已验证有效的协作模式】
A1. 阶段冻结 + 小闭环推进

将整体目标拆解为 Phase → 子阶段（如 Phase 2.5），并在每一阶段明确“冻结点”

每个阶段只追求一个“可运行、可人工验证”的小闭环

明显减少了“边做边改方向”的返工风险

抽象原则：

在人机协作中，阶段性冻结目标，比一次性追求完整度更高效。

A2. Prompt 工程化（可执行 Prompt 而非描述性需求）

所有关键任务均转化为 Cursor Agent 可直接执行的 Prompt

Prompt 中明确：角色、边界、禁止项、完成标准

大幅降低 AI“自由发挥”导致的偏差

抽象原则：

AI 协作中，“指令即接口”，Prompt 需要像工程接口一样被设计。

A3. TDD 作为人机协作的稳定锚点

明确要求：先测试、后实现

测试成为 AI 自我校验和人类 Review 的共同语言

在逻辑复杂度上升时（SN / 绑定规则），显著提升稳定性

抽象原则：

在 AI 参与实现时，TDD 不只是质量工具，更是协作约束机制。

A4. 规则先行、实现后置

在实现校验逻辑前，先冻结《规则文档》

再将规则翻译为伪代码 / 决策树

AI 只负责“实现规则”，不参与“定义规则”

抽象原则：

人类负责“定义不可讨论的规则”，AI 负责“高保真执行”。

A5. 允许阶段性“战术回退”

当隐藏 TextBox 等方案引入不稳定性时，果断回退

不强行“一次成功”，而是保留技术债到合适阶段解决

抽象原则：

人机协作中，及时止损与回退是成熟决策，而非失败。

【B. 人类的稳定偏好】
B1. 偏好结构化、冻结式决策

明显倾向：先讨论 → 反驳 → 冻结 → 执行

不接受“边做边想”的模糊状态

稳定偏好：

更信任“被明确写下来的规则和边界”。

B2. 偏好工程可落地，而非概念正确

多次强调：能跑、能测、能人工验证

UI、流程、逻辑均以“操作员真实使用”为评判标准

稳定偏好：

偏向工程实用主义，而非理论完美。

B3. 偏好 AI 自执行 + 人工 Review

倾向让 AI 批量执行，再人工 Review 与纠偏

人类不做重复劳动，只做判断与决策

稳定偏好：

人类负责判断质量，AI 负责消耗执行成本。

B4. 对“经验沉淀”高度敏感

多次主动提出“是否值得写入记忆”

明确区分：一次性经验 vs 可复用原则

稳定偏好：

重视长期复利，而不是单次任务完成。

【C. 可改进或需避免的协作方式】
C1. 过早并行多个不稳定方向

如 UI 隐藏输入框、输入法切换、ScanInputService 抽象同时推进

在基础尚未稳定时，容易放大调试成本

改进方向：

在人机协作中，并行只适合“低耦合、低风险”模块。

C2. Canvas / 工具异常导致上下文中断

多次出现 canvas 内容未生成或丢失

造成重复生成与心智负担

改进方向：

关键规则与 Prompt，应有本地文档作为最终事实源（Single Source of Truth）。

C3. UI 目标初期略显模糊

“简约大方”在早期仍有解释空间

后续通过“结果卡片 / 工业 UI 共性原则”才收敛

改进方向：

UI 协作中，应尽早转化为“可识别性 / 操作性”等客观目标。

【长期记忆候选】
✅ 值得长期保留的原则

阶段冻结 + 小闭环推进 是高效人机协作的核心节奏

Prompt 工程化 是 AI 可控性的关键

TDD 在 AI 协作中是约束工具，而不仅是测试方法

规则先行、实现后置 能显著降低歧义与返工

SN / 包装 / 设备的具体业务规则内容（但“规则冻结方式”可复用）

本次协作的价值，不在于“做了一个上位机”，而在于验证了一套可规模化、可复制的人机协作工程方法。

【A. 已验证有效的协作模式】
先读约束 / 文档，再动手改 UI
在你明确指向 SnVerify_UI_Design_Constraints.md 之后，先通读并对照现状，再做改动，避免了“做完再被推翻”的无效迭代。
这说明：当用户给出设计/架构约束文件时，AI 应优先把它当作 Single Source of Truth，而不是事后查阅的参考。
小步可视化迭代，而不是一次性大改
UI 重构过程基本遵循“一个局部、一两个参数”的微调：
例如：
先调整 SN 区域宽度与截断方式
再单独调主卡片尺寸与圆角
再调失败区域高度、再挪扫码输入位置
这种“局部 + 快速验证”非常适合 UI 场景，能让你在 IDE 里即时预览效果，也方便你随时把某一块手动改回。
可泛化为：UI/交互相关任务，优先采用“局部小步 + 用户肉眼确认”的节奏，而不是一次性大手术。
保持测试与实现同步的改动套路
修改 Excel 表头文案时，同时：
改实现："SN" → "条形码SN"，"DeviceSN" → "设备SN"
用搜索快速定位相关测试断言，并同步更新
这是一个好的协作模式：凡是可预测影响测试的改动（文案、列名、状态字符串等），AI 应自动搜索测试里相关字符串并一起调整，而不是等测试失败后再补。
前端调整优先保持数据/业务层不动
你先强调“不改业务逻辑，只动 View / 绑定”，整个过程中也确实做到了：
改变的是 XAML 布局、样式、绑定显示方式，而非流程或规则。
这说明一个稳定协作原则：当用户明确界面层任务时，AI 应把“不可动层”当作强约束，哪怕有更优的业务重构方案也先不触碰。
异常优先精确定位 + 最小修复
XAML 报 ErrorDetailPanelStyle 找不到时，没有大范围重构，而是：
先用行号/样式名快速定位
补回丢失的样式定义，尽量沿用当前紧凑风格
这是一个通用协作模式：对运行时异常，先做“精确修补 + 保持当前设计意图”，而不是顺手大改 UI 结构。
【B. 人类的稳定偏好】
偏好工业风 UI：功能清晰优先，装饰性有限制
多次强调“工业上位机、产线、简约、稳定”、“不要动画/渐变/第三方框架”，只在允许范围内做拟物感和醒目效果。
这体现为：用户倾向于“高对比 + 明确状态色 + 结构稳定”，而非花哨视觉。
喜欢“明确说明 + 精准修改”的反馈方式
你通过 @文件 @行区间 精确指向问题区域，并用“高度小一些、放到某区域之间”这样的指示来驱动改动。
你并不需要长篇解释，更在意“我改了哪里、改成什么效果”，因此 AI 的简短中文总结（列出关键属性变更）是契合你风格的。
愿意手动微调，但希望 AI 打好基础
多次在我调整后，你自己又对字号、MinHeight 等做小改动（例如把 56 改成 48，把 MinHeight 350→300）。
这说明：你希望 AI 提供合理基础方案和结构，让你能在 IDE 中肉眼看效果、做 10% 的手工细修。
重视“布局逻辑”一致性
你持续推进布局逻辑更符合你脑中的结构：
批次区 + 扫码入口在顶部
主区：状态卡片 → 扫码框 → SN 信息 → 错误
日志可折叠，状态栏固定底部
这表明：你对视觉/布局“信息层级”的一致性非常在意，比单个控件样式更重要。
【C. 可改进或需避免的协作方式】
UI 大改时一次改动过多，容易引入遗漏
在一次合并修改中，曾经同时：
改失败区域样式
删了 ErrorDetailPanelStyle
下方仍然引用该 StaticResource
结果引出 XamlParseException，需要额外一轮修复。
可改进为：对 WPF 这类强依赖资源字典的项目，批量改样式时保持“增量而非删除重建”，或改完立刻做一轮针对常见资源名的自查（搜索引用）。
布局结构大改时，先计划再下手会更稳
从 Grid 转 DockPanel 的重构是正确的，但如果事先写一个简短“目标结构”（Top: 批次+扫码, Middle: 主检验, Bottom: 日志, Bottom-most: 状态栏），可以减少来回调整。
通用建议：当需要调整根布局（DockPanel / Grid / StackPanel 切换）时，AI 可以先以 3~5 行文字给出“新布局骨架”，经你认可后再落地代码。
命名/样式资源的生命周期要显式管理
ErrorDetailPanelStyle 的删除/恢复暴露出一点：AI 没有显式管理“样式资源表”，导致误删。
可优化为：在删除或重命名样式资源前，AI 应总是先全局搜索引用，并在总结中明确指出“此样式不再需要/已全部替换”。
