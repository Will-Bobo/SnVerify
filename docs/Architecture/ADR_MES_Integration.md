# ADR-001：MES 集成架构决策

## 状态

* 状态：已记录（Deferred Implementation）
* 决策时间：Phase 2 执行期间
* 生效范围：上位机核心流程（Phase 2 及以后）

---

## 一、背景（Context）

当前上位机在 Phase 2 阶段已开始接入 MES 能力，本次对接对象为 **杰科工厂 MES**。但从系统生命周期和产线实际使用情况来看：

* 未来可能需要对接 **多个工厂 / 不同 MES 协议**
* 上位机在 **调试、试产、离线、MES 不稳定** 场景下，必须能够独立运行
* 过早将具体 MES 实现（如杰科）写死在业务流程中，会显著增加后续演进成本

因此，需要在当前阶段明确 MES 的总体架构策略，但不急于完成最终实现。

---

## 二、问题（Problem）

如果在 Phase 2 直接将 MES 逻辑强耦合到业务流程中，将带来以下风险：

1. **可扩展性差**：新增工厂或更换 MES 成本高
2. **系统稳定性风险**：MES 异常会阻断核心检验流程
3. **测试与调试受限**：无法在无 MES 环境下完整测试
4. **职责混乱**：业务流程与外部系统协议耦合

---

## 三、决策（Decision）

### 1️⃣ MES 通过中间抽象层接入

* 系统仅依赖抽象接口（如 `IMesService`）
* 不直接依赖任何具体 MES 实现（如杰科 MES）
* 不同工厂 MES 以 **Adapter / Provider** 形式接入

> 结论：**MES ≠ 杰科 MES，杰科只是一个实现**

---

### 2️⃣ MES 作为“可选依赖”，支持开关控制

* 系统启动时可配置 MES 是否启用
* MES 关闭时：

  * 不进行任何网络调用
  * 不影响扫码、ADB 校验、结果判定等核心流程

示例配置（概念）：

```yaml
Mes:
  Enabled: false
  Provider: JieKe
```

---

### 3️⃣ 当前阶段不完成最终 MES 对接

* Phase 2：

  * 仅验证架构位置正确
  * 允许存在最小 Stub / Mock / No-Op 实现
* 最终对接与稳定性优化：

  * 延后至 Phase 3 / Phase 4

---

## 四、影响（Consequences）

### 正面影响

* 业务流程与外部系统解耦
* 支持离线 / 调试 / 试产场景
* 为多工厂扩展预留清晰边界
* Cursor Agent 后续生成代码有明确架构约束

### 代价

* 需要维护一层抽象
* 初期代码量略有增加

> 该代价在中长期显著小于后期重构成本

---

## 五、实施策略（当前阶段）

在 Phase 2：

* ✅ 记录该架构决策（本文件）
* ✅ 确保业务层 **不假设 MES 一定存在**
* ❌ 不要求实现完整 MES 适配
* ❌ 不要求处理所有 MES 异常分支

---

## 六、后续计划（Future Work）

* Phase 3：

  * 定义 `IMesService` 稳定接口
  * 引入至少一个真实工厂实现（杰科）

* Phase 4：

  * 支持多工厂配置
  * MES 失败降级策略
  * 日志与追溯能力增强

---

## 七、备注

该 ADR 为 **冻结决策**：

> 在 Phase 2 完成前，不对 MES 架构做方向性调整，只允许补充说明。
