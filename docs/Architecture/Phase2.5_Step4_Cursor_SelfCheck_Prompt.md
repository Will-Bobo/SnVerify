# Phase 2.5 – Step 4 Cursor Agent Self-Check Prompt

> 目标：在 Cursor Agent 执行 Phase 2.5 Step 4（MES 插件接入与 Post-Report 异常处理）时，自行校验生成内容是否符合设计规则与冻结约束。

---

## 自检规则（10 条）

### 1️⃣ MES 插件接口是否符合约束
- **IMesClient**：是否只提供 `CheckConnectionAsync` 和 `ReportTestResultAsync` 这两个方法
- **IMesGate**：是否通过 `EvaluatePreTest` 来决定是否允许执行测试
- 是否遵循 “插件化” 设计，MES 插件不应修改核心逻辑
- 是否正确处理 **Pre-Test** Gate 逻辑，MES 不应直接影响数据生成

### 2️⃣ MES 事件通知机制
- **Post-Report 失败时**，事件是否成功通知 UI（如 `MesEvent`）
- 事件类型包括：`ReportFailed`、`ConnectionLost`
- 确保事件不直接影响 PASS / FAIL 结果，仅作通知用途

### 3️⃣ Session 和 Order 数据一致性
- 确保 **Session** 与 **Order** 的数据保持一致性
- 对 **Order** 的任何修改都应通过 **Session** 内的状态管理来实现
- 确保每个 Session 与 Order 关联正确，避免数据丢失

### 4️⃣ Post-Report 失败时的 UI 反馈
- 确保 **Post-Report 失败** 仅通过日志或事件反馈，**不影响测试流程**
- UI 是否提供简洁的“失败”反馈，并清楚区分 **业务失败** 与 **报告失败**
- 不应阻塞 UI 或测试流程，仅提供“信息”提示

### 5️⃣ 防抖逻辑验证
- 确保防抖机制在 **Post-Report 失败** 时正确触发，避免重复报告
- 确保防抖机制在 UI 层执行，确保不会多次点击按钮触发同一操作

### 6️⃣ UI 与业务流程的解耦
- UI 层是否完全解耦于业务逻辑（如是否有 `TestRecord` 和 `Session` 直接操作 UI 控件）
- 所有业务判断（如是否提交到 MES）是否通过 **业务逻辑层** 或 **Gate** 实现

### 7️⃣ 异常路径测试
- 处理 Post-Report 失败的错误路径是否经过彻底测试
- **设备 SN 不一致**、**超时**、**连接丢失**等异常是否被正确处理并反馈
- 确保异常信息简洁，能够快速定位问题并修复

### 8️⃣ 流程完整性与数据一致性
- 确保测试流程完全按照设计执行，**每个流程节点都应有明确的状态**
- **Session** 和 **TestRecord** 数据是否在 UI、日志、导出文件中一致
- **TestRecord** 的状态（PASS / FAIL）是否在流程中一直有效

### 9️⃣ 数据导出与报告生成
- **导出功能**是否支持按 Order 和 Session 导出数据，且数据正确
- 导出数据时，确保不会重复生成文件，且不会覆盖已存在的文件
- 确保 **报告导出** 时数据的 **格式一致性** 与 **完整性**

### 🔟 代码和文档的规范性
- **代码注释**是否覆盖所有 public 类和方法
- **API 接口文档**是否包含完整的说明、用途和参数示例
- 是否遵循命名规范并确保一致性，避免混乱的命名与结构

---

## 使用方法

1. Cursor Agent 在生成 Step 4 代码后，自动检查每条规则是否被满足
2. 不满足规则的部分必须在代码注释中标注 TODO 或 Issue
3. 所有规则通过后，Step 4 才算完成，进入最终集成与部署
