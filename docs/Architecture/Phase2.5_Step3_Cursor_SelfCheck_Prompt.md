# Phase 2.5 – Step 3 Cursor Agent Self-Check Prompt

> 目标：在 Cursor Agent 执行 Phase 2.5 Step 3（UI 重构与行为设计）时，自行校验生成内容是否符合冻结约束和设计规则。

---

## 自检规则（12 条）

### 1️⃣ UI 交互是否符合设计
- 确保 **PASS / FAIL** 高亮显示且正确
- 确保日志区域折叠功能正常，且显示最近 N 条记录（如 1000 条）
- 确保 UI 元素按状态启用或禁用，防止重复点击
- 自动检验与手动检验按钮逻辑应独立，互不冲突
- 状态栏能实时更新，反映当前测试状态（例如，“等待中” / “测试中”）
- 错误提示区仅弱提示 MES 上报失败或设备错误，且不会阻断当前操作流
- 按钮防抖机制需确保重复点击无效

### 2️⃣ UI 行为与 ViewModel 分离
- 所有状态更新通过 ViewModel 绑定完成，不应直接修改 UI 控件
- ViewModel 管理状态机和逻辑处理，UI 仅做显示与交互
- UI 事件（如按钮点击、状态更新）通过 ViewModel 进行响应
- 所有 UI 控件应能正确响应状态变化（如按钮禁用、显示 PASS/FAIL）

### 3️⃣ 状态与流程控制
- 自动检验时，操作按钮禁用，直到当前 SN 流程完成
- 自检按钮与主检验按钮互斥，不应并发触发
- 流程中状态更新（等待中、测试中、完成等）应及时更新 UI

### 4️⃣ 错误处理与提示
- MES 上报失败时，仅记录日志，UI 提示不影响业务流程
- 设备错误时，UI 提示设备 SN 已存在，错误提示不应阻塞操作
- 重复操作（如 Start / End）时，UI 仅显示一次错误信息，不重复提示

### 5️⃣ 防抖逻辑与重复点击判定
- 确保 Start / End 按钮的防抖机制正常，重复点击无效
- 重复点击需要通过状态机确认是否生成有效的 TestRecord
- 自动检验按钮与手动检验按钮需要正确禁用，避免并行操作

### 6️⃣ UI 异常反馈
- 确保 **Post-Report** 失败时能够通过事件反馈，而不是直接修改 PASS/FAIL 状态
- UI 异常提示应该简洁明了，不阻塞业务流，确保操作员能看到有效信息

### 7️⃣ UI 显示与用户交互一致性
- 确保所有操作反馈（如测试开始/结束）与 UI 状态显示一致
- 测试完成后，UI 需要显示测试结果并更新状态
- **PASS** 与 **FAIL** 反馈应清晰、可操作，避免信息过载

### 8️⃣ 状态栏与日志区域
- 状态栏需要提供实时反馈，显示当前测试状态（“测试中”，“完成”）
- 日志区域需要显示用户的每次操作，确保信息透明化
- 日志区域显示不应影响测试的实时流程

### 9️⃣ UI 数据绑定与验证
- UI 应该正确绑定 ViewModel 的状态数据，不直接访问业务数据层
- 所有 ViewModel 中的字段需要通过数据绑定正确反映 UI 状态

### 🔟 单元测试覆盖
- 确保 UI 状态、按钮启用禁用、日志显示等功能都有对应的单元测试
- 需要覆盖正常路径（点击 Start/End），异常路径（设备错误、MES 上报失败）
- 确保防抖机制、状态变化等场景的测试覆盖

### 11️⃣ 错误信息显示规范
- 确保错误信息简洁，且按照优先级（比如 MES 异常与设备错误分开）显示
- 错误信息需要支持快速修复的提示，避免操作员困惑

### 12️⃣ 代码规范
- 所有 public 类 / 方法必须有 XML 注释
- 禁止直接修改 View 或 UI 控件
- 禁止使用 `Application.Current`、`Dispatcher` 或其他影响 UI 的线程调度方式
- 所有 UI 组件和 ViewModel 属性需要符合命名规范，并在设计时做统一约束

---

## 使用方法

1. Cursor Agent 在生成 Step 3 代码后，自动检查每条规则是否被满足
2. 不满足规则的部分必须在代码注释中标注 TODO 或 Issue
3. 所有规则通过后，Step 3 才算完成，进入实际的 UI 流程实现
